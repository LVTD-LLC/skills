# Code Sample Knowledge

Code samples help developers understand, evaluate, and use a product. They also create risk when they are stale, unclear, untested, or unrealistic.

Source basis: *Docs for Developers*, Chapter 5, "Integrating code samples."

## Sample Types

| Type | Purpose |
|------|---------|
| Executable sample | Lets readers run or adapt working code |
| Explanatory snippet | Illustrates one concept or API behavior |
| Request/response pair | Shows exact API input and output |
| CLI command | Demonstrates command syntax and expected behavior |
| Config example | Shows required structure and values |
| Generated sample | Derived from schema or source code, then reviewed for usability |

## Quality Dimensions

| Dimension | Meaning |
|-----------|---------|
| Explained | The reader knows prerequisites, purpose, limitations, and why it works |
| Concise | The sample includes the exact information needed and little else |
| Clear | Names, style, formatting, and control flow are understandable |
| Usable | Placeholders, setup, inputs, and outputs are realistic and copyable |
| Extensible | Readers can adapt the sample without reverse engineering it |
| Trustworthy | The sample is tested, reviewed, version-aware, and not misleading |

## Maintenance Concerns

Multiple languages, generated examples, sandboxes, and SDK versions can increase maintenance load. Every code sample should have a source of truth and a way to detect drift.

## Common Misconceptions

- **Myth**: Autogenerated examples remove the need for review.
  **Reality**: Generated samples still need human checks for usefulness, naming, context, and reader fit.
- **Myth**: A sample is better if it covers many use cases.
  **Reality**: New users often need narrow examples; advanced users need focused advanced examples.
